# Permissions

Explicit and semantic permissions with reviewed overrides and authoring change sets implemented for current tools, 2026-10-21 · [Delivery and verification](../../docs/plans/permissions-decisions-tests.md)

[Product principles](../product.md) · [Decisions](decisions.md) · [Engineering design](../../docs/features/permissions.md) · [G08](../open-questions.md#g08--identity-permissions-and-decisions)

## Goal

Let the user establish Ash's authority through visible permissions and explicit Decisions, then enforce that authority against the actual action. Ash has one primary user; a general-purpose permissions administration interface is outside this scope.

## Scope

Includes deterministic resource restrictions, semantic conditions, permission authoring and formalization, user authorization, sensitive-action discovery, and the permission-request boundary with Decisions. Initial UI categories are Filesystem, Computer use, Interaction and Self-modification.

Permissions owns saved permissions, their interpretation, authorization and action evaluation. [Decisions](decisions.md) separately owns requests for user input and their responses. Their handoff below applies across features; self-modification is a future consumer, not the starting workflow.

Private-data handling, evaluator disclosure policy and retention/erasure policy are deferred to a separate security/privacy design. They are outside this feature review; sensitive-action discovery remains part of Permissions.

The [engineering design](../../docs/features/permissions.md#current-implementation) identifies the implementation and policy shape. The [selected evaluator](../../docs/features/permissions.md#selected-evaluator), Decision integration and durable continuation retain their existing contracts.

The accepted [tool slice](tools.md#initial-filesystem-tools) stages configured filesystem access through a common authorization boundary. Its limited scope enforcement precedes the full evaluator and permission UI; it does not claim completion of the permissions below.

## Flow

1. The user describes a permission in natural language or uses a verb + resource picker. Ash proposes one or more permissions and their Allow / Ask / Never settings; each permission is explicit or semantic.
2. Review complete matching scope, any wording improvement and proposed semantic override relationships before saving. Exact conditions become explicit permissions; qualified conditions requiring interpretation stay together as semantic permissions.
3. When preparing an action, Ash checks its actual targets and effects against applicable permissions and existing authorization. The sensitivity check also looks for consequential effects that existing permissions have not addressed.
4. Allowed work proceeds. Work with an effective Ask permission waits for explicit confirmation through a Decision, even if the user already requested that exact action. The Decision describes the concrete action and relevant restriction or newly detected concern.
5. The user can authorize this work or explicitly establish a standing permission. For a newly detected concern, Ash proposes a general permission; after the user resolves it, Ash reevaluates the pending action.

## Permission behavior

- **PERM-R01 — Sources of authority:** setup establishes clearly described ordinary access through visible, editable permissions; user requests establish intended work and its ordinary necessary steps, subject to those permissions. A request cannot substitute for an Ask confirmation under PERM-R11 or override a deny under PERM-R19. App/API connection scopes use the controls in PERM-R20. Setup defaults are adopted below.
- **PERM-R02 — Configurable defaults:** start with Allow for Prepare drafts in Ash and Use computer, and Ask for Send messages and Publish public content. Also seed global Never permissions for common secret filenames (`**/.env*`, `**/*.pem`, `**/*.key`) and a semantic Never permission for reading secret values. Do not block `.git`, `.ash-dev`, `out` or `node_modules` merely because they are internal/generated folders. These are editable initial permissions, not permanent restrictions or guarantees; the user can narrow, replace or remove them. Draft and delivery permissions are distinct. Existing authorization follows PERM-R11. These defaults supersede the corresponding original prohibition in [HUMAN_SPEC.md](../HUMAN_SPEC.md).
- **PERM-R03 — Effects:** permissions express Allow, Ask or Never, stored as `allow`, `ask` or `deny`. Allow permits a matching action once the other checks pass; it does not override independent restrictions. Ask requires explicit confirmation through a Decision under PERM-R11; Never disallows the matching action. Resolve narrower permissions under PERM-R07/R26 before combining effects. A direct request does not override a deny; one-time exceptions and changes follow PERM-R19.
- **PERM-R04 — UI categories:** each permission belongs to exactly one category, assigned when created; permissions cannot move between categories. Start with Filesystem, Computer use, Interaction and Self-modification. Category membership is excluded from enforcement, classifier input and permission-candidate selection; there are no multiple category labels on a permission.
- **PERM-R05 — One Permission, one condition:** each Permission has one effect and either an explicit verb + resource matcher or one complete semantic condition. There is no resource/activity distinction, permission container or mixed explicit-plus-semantic policy. Derive its name from the explicit verb/resource or accepted semantic action phrase; do not store a separate name. Semantic conditions retain all qualifications, including exact paths or identities mentioned within them. UI category does not alter matching.
- **PERM-R06 — Faithful formalization:** accept natural language and a verb + resource picker for explicit permissions. Natural language may propose individually reviewable additions, changes and removals involving explicit or semantic permissions. Put clearer wording directly in the proposed permission, preserving the described meaning; do not show a separate Suggested wording block. Review each permission's complete scope, effect and any overrides under PERM-R26 before saving. Each suggested addition or change has an editable Access picker; every suggestion has a keep checkbox, including a single suggestion. Start with all additions, changes and removals selected; unchecking retains the draft but excludes the operation from Save. Revalidate the selected final permission set and affected relationships before saving. Omit links to unselected new broader proposals; existing broader permissions remain active. Save accepted meaning once in policy, without an original-text copy. Do not split conjunctions or qualifications when that broadens their meaning. For new permissions, propose broad permissions plus linked narrower overrides for exceptions and different access levels; avoid complement/exclusion-heavy partitions. Preserve the restricted scope in each exception; it cannot become an unrelated blanket allowance. Recognize named-entity specificity automatically during authoring and propose priority over general membership groups; do not ask whether a named exception still applies when membership also matches. Prefer one permission for multiple named recipients with identical access and overrides. Do not create an extra intersection permission merely to establish priority. Reuse unchanged saved permissions and their IDs instead of suggesting duplicates, including explicit/semantic equivalents. Equivalent scope with different intended access proposes a change to the existing permission, preserving its ID and category, rather than an equal-scope override. Suggest removal of relevant redundant permissions with any necessary override rewiring; show additions, before/after changes and removal impact before Save. Collapse identical generated proposals and remap their override references; reject contradictory access for the same scope. If no change is needed, show that the permissions are already saved. Clarify consequential ambiguity; include identifying details in accepted wording where useful, such as “John Smith (john@example.com).” No contact/entity store is required initially. A model change cannot silently rewrite saved meaning.
- **PERM-R07 — Filesystem:** use explicit filepath permissions and canonical-path, most-specific-ancestor inheritance for the same verb. A more specific permission replaces its ancestor's effect, including Ask or Never; unrelated verbs and semantic restrictions still apply under PERM-R21/R26. Equal-specificity matches combine by effect precedence. Read, list, glob, grep, write, edit, mkdir, move and delete remain distinguishable. A move covers both source and destination and is presented as one action when permission is needed. Default to editable read-only access to Ash's current code directory (`list`, `read`, `glob`, `search`), accepted 2026-10-14. The Resource field accepts a file, folder or path glob: infer existing file/folder scope; a missing literal path names one future file unless it ends in `/`, which includes the future folder and contents. `*` and `?` stay within one name; `**` spans directories. A glob matches the complete path; a trailing `/**` includes a matched folder and contents. Compare the depth of the matched component; a deeper fixed root breaks glob ties, and a literal path wins over a pattern at equal depth. Preserve legacy recursive name-pattern behavior for existing permissions. Retained policy exclusions appear as explicit permissions. A broad traversal omits Never descendants and reports the omission; directly requesting a blocked target still requires PERM-R19. Ask descendants continue through Decision controls. Runtime/provider capability limits remain separate from policy; Allow creates no missing capability. Migration must preserve existing effective access under the [migration design](../../docs/features/permissions.md#migration).
- **PERM-R08 — Computer use:** initially provide one editable Use computer permission (Allow / Ask / Never), defaulting to Allow within available computer capabilities. Sending and publishing restrictions still apply. Computer-control tools are separate delivery work. For the same computer-use verb, an explicit application identity overrides the general computer scope; other verbs and independent restrictions still apply. Distinguish observing an application from controlling it. Application identity and access are deterministic where the runtime can establish them; the meaning of an interaction may require semantic evaluation.
- **PERM-R09 — Effects across tools:** using another tool does not bypass a restriction. For example, browser control does not itself authorize contacting someone, and terminal access does not override a protected filesystem scope. The enforcement mechanism must cover the route used; classifier agreement alone cannot establish that coverage.
- **PERM-R10 — Evidence and authority:** evaluate the concrete proposed action with relevant evidence and user authorization. External documents, pages and tool results cannot grant permission. Missing evidence stays explicit. The accepted [context guidelines](../../docs/features/permissions.md#classifier-context) govern what reaches a classifier.
- **PERM-R11 — Permission requests:** revised and accepted 2026-10-14. An effective Ask permission always requires explicit user confirmation through the Decision's approval controls, even when the user prompt requests the exact action. Chat text, including a later “yes,” and model inference cannot resolve that permission Decision. Identify the action, target and material consequences being approved. A still-valid approval can satisfy repeated checks of the same pending action; a new action needs its own confirmation. A one-time approval does not become a standing permission. This supersedes the earlier permission that an explicit request could satisfy Ask.
- **PERM-R12 — Uncertainty and changes:** gather missing evidence or use further evaluation when useful. If authority remains unresolved, hold the action for a Decision. Evaluator errors do not grant permission. Recheck when material action details, evidence or effective permissions change before execution; a previous approval cannot silently cover a different recipient or payload.
- **PERM-R13 — Inspection:** retain the evaluated action, permission snapshots, explicit scope winners, applied semantic overrides, authorization used, classifier evidence/results, model version and final outcome sufficiently to explain the check. Exclude credentials and private model reasoning. Storage and retention remain design work under G06/G09; this does not introduce general application-edit audit history under [ART-R10](artifacts.md#rules).
- **PERM-R14 — Sensitive-action discovery:** the sensitivity check looks for sensitive consequences not adequately addressed by existing permissions or informed authorization before execution, even if the action matches no permission or a broad allow. A credible unresolved concern holds the action and produces a Decision with the reason and a proposed standing permission. Generalize the relevant boundary across incidental recipients, tools or sites without extending it to unrelated activity. The user accepts or edits the proposal before it becomes a permission; Ash cannot silently create one. Apply PERM-R06, then reevaluate the action: accepting a deny prevents execution. A detector's concern is not a permanent prohibition. Do not repeat a question whose sensitive consequence the user has already explicitly addressed unless material facts change.
- **PERM-R19 — One-time exceptions:** after narrower-permission resolution under PERM-R07/R26, a remaining deny requires an explicit exception to the identified restriction or a permission change. An ordinary request for the blocked action is insufficient. A one-time exception records its scope and identified restrictions on a Decision; other restrictions still apply. It does not rewrite a standing permission or establish an override relationship. Lifetime follows PERM-R23; scope and consumption follow the [execution contract](../../docs/features/permissions.md#approval-data-on-decisions).
- **PERM-R20 — Connection controls:** app/API setup presents relevant resource/operation scopes as ordinary permissions with an **Allow / Ask / Never** picker. For example, connecting selected calendars can initialize an Allow permission for reading those calendars; the user can change it during setup or later. Never means deny, not removal of the permission. Keep different capabilities distinguishable, and show the actual account/resources covered. Provider-granted capabilities and Ash's permissions are separate: an Allow cannot supply a capability the connection lacks. Detailed scope grouping remains PERM-Q01.
- **PERM-R21 — Combined permissions:** account for every relevant Permission across the work's actions, targets and consequences. Resolve explicit filesystem specificity under PERM-R07 and reviewed semantic overrides under PERM-R26, then one-time exceptions under PERM-R19. Combine remaining applicable effects with **Never > Ask > Allow** precedence. Mere semantic specificity supplies no override. A permission covering John cannot suppress restrictions on another recipient in the same send; combine their outcomes before executing. An Allow or Ask match cannot end evaluation while another relevant restriction remains unresolved. A task-level allowance does not bypass its individual action checks; satisfying Ask follows PERM-R11.
- **PERM-R22 — Default allowance:** an action does not need a matching Allow permission. Within available runtime/provider capabilities, it may proceed once applicable restrictions under PERM-R21 and sensitive consequences under PERM-R14 are resolved. Lack of a permission or unfamiliarity alone does not require a Decision. Failed or incomplete checks remain governed by PERM-R12.
- **PERM-R23 — Approval lifetime:** a one-time approval has no automatic expiry. It remains valid across delays, disconnections and restarts for the same pending action while nothing material has changed. Revalidate current permissions and material facts under PERM-R12 before execution. Continued validity does not authorize repeating a completed action; retries follow PERM-R25. A saved approval never revives cancelled work.
- **PERM-R24 — Immutable approvals:** approval responses follow [DEC-R12](decisions.md#rules). There is no approval-withdrawal control or separate revocation lifecycle; stopping dependent work uses ordinary cancellation under DEC-R13.
- **PERM-R25 — Approval reuse for retries:** reuse a still-valid approval for the same action when the previous attempt is confirmed to have had no effect and current checks pass. If the previous outcome is unknown, establish it before retrying; keep the action held while uncertainty remains. A failure or timeout alone does not establish that nothing happened. Preserve attempt history and do not repeat completed effects. This defines approval reuse, not automatic retry scheduling or limits.
- **PERM-R26 — Reviewed semantic overrides:** revised 2026-10-14. A semantic Permission may take priority over named Permissions for their shared matching action/target/consequence. Strict containment is sufficient, not required: an identified recipient can override a semantic recipient group without asserting membership. For example, a John/Amy Allow can override CRM friends Ask and general Send messages Never. Ash suggests specificity and exception relationships during authoring; the user reviews the selected permissions, named targets and outcome examples before Save. Preserve independent restrictions: a generic recipient allowance cannot override an external-work-file prohibition without retaining that separate sensitive consequence in an authorized exception. Equal scopes should be one permission; unrelated actions and disjoint scopes cannot form overrides. Save validates compatibility and graph invariants before atomic commit. Concurrent changes to displayed permissions/effects require updated impact and another Save. Only a definitely matching permission supplies priority, within its covered targets/consequences. A named overridden condition's uncertain membership cannot block that definite exception; uncertainty in the exception or any independent permission still holds the action, and evaluator failures remain blocking. Runtime uses saved links, not inferred prose specificity. Unlinked permissions combine under PERM-R21. References must be active, distinct, non-self and acyclic. Review affected relationships on scope/effect edits and clean references on retirement. Capability, Ask and sensitivity checks retain authority.

## Permission management

Management and integration follow the accepted permissions above.

- **PERM-R15 — Manage permissions:** revised 2026-10-14. Permissions lives in the Settings modal as a tab alongside Instructions. Use the shared [Settings layout](instructions.md#rules). Its category views are keyboard-accessible tabs. Use a headerless list with derived verb + resource names and inline Allow / Ask / Never pickers. Show complete paths and semantic qualifications with wrapping; meaningful conditions must not depend on ellipses, hover or opening the editor. A compact “Overrides” line links to the broader permissions and shows their effects. Put an add icon beside category tabs and a pencil beside each name, revealed on hover or keyboard focus and always available on touch devices. Offer natural-language creation through Suggest permissions and an explicit picker limited to Filesystem and Connections. Describe mode has no shared Access input. Put each suggestion’s unlabeled Access picker at its top right, with an accessible name; omit the Category input. Selection belongs to each suggestion. Show suggested overrides in a compact table with separate Permission, Access and remove columns, plus an Add override list. Save permissions validates and atomically applies only selected additions, changes and removals, including their Access and override edits. Show Add/Change/Remove, before/after changes and removal impact under PERM-R06. Distinguish Add with a green plus, Change with an amber pencil and Remove with a red minus, retaining text labels so meaning does not depend on color. Disable Save when none are selected; require no separate Review overrides step. Put Resource Type, Resource and Action on one row, then Access below. Infer filesystem scope and accept wildcards in Resource; expose no separate Scope or Name pattern controls. Save ordinary explicit permissions directly after backend validation. Review affected override relationships before commit; do not require a generic Review interpretation step. Effect-only changes save immediately with a visible result when no relationships are affected; otherwise review under PERM-R26. Authoring review shows complete scope, affected permissions and example outcomes; editing afterward invalidates it. Put removal in the editor with impact confirmation. Keep technical JSON and classifier metadata out of these controls. Unsupported or ambiguous interpretations stay inactive. Save current state without version history; earlier evaluations retain their snapshots.
- **PERM-R16 — Deliberate policy changes:** authorizing one action and saving a standing permission are distinct operations. A permission Decision may offer both, but it must show which will change. Saving a permission uses the same interpretation review as the permission editor; saving a permission does not itself execute pending work. Ash may propose changes but cannot silently activate them.

## Decision handoff

Permissions returns an evaluation of a concrete action; it does not require a Thread, present UI or execute the action. Distinguish a permission's `allow`/`ask`/`deny` effect from the result of evaluating current permissions, evidence and authorization:

| Evaluation result | Caller behavior |
| --- | --- |
| Allowed | Execute only while the evaluated action, evidence and authority remain valid and the execution adapter can enforce its limits. No Decision is needed. |
| Denied | Do not execute; explain the effective restriction. An ordinary Approve button must not silently override a deny. Any exception must meet PERM-R19. |
| Needs user input | Hold dependent work and create a Decision identifying the missing authorization, clarification or sensitive-consequence response. |
| Blocked | Hold work because evaluation or enforcement cannot complete. Preserve the error/unknown facts separately; a bare approval cannot repair a failed check or establish missing material evidence. Request a user remedy through Decisions when useful. |

- **PERM-R17 — Request and answer:** supply the caller with the action and relevant evidence, evaluated permission snapshots, reason, required input and any inactive permission proposal. The caller persists one Decision for the same outstanding requirement; reconnects and repeated checks do not create duplicate questions. A valid response becomes evidence or scoped authorization for reevaluation, never a replacement for it.
- **PERM-R18 — Action binding:** identify the requested operation, targets, payload and material consequences independently of the UI summary. Bind any one-time approval to that action. Freshness follows PERM-R12; lifetime, immutable approvals and retries follow PERM-R23–25. Scope and consumption follow the [execution contract](../../docs/features/permissions.md#approval-data-on-decisions). Declining an action supplies no authorization and creates no standing deny unless the user explicitly saves one.

Permission errors and unanswered questions can both hold work, but the user must be told which problem needs resolution. The [Decision lifecycle](decisions.md#lifecycle) and [continuation contract](decisions.md#continuation) own request state and delivery to waiting work.

## Open decisions

The routine defaults below are adopted; engineering contracts are in the design. Private-data policy and new capability adapters remain separate work.

- **PERM-Q01 — Defaults:** default allowance follows PERM-R22 and connection controls follow PERM-R20. **Defaults:** preserve effective filesystem access and fixed Topic capability boundaries during migration under PERM-R07; retain read-only Ash code and general Computer use defaults. Group connection controls by account/resource and meaningful capability, keeping reads and mutations distinct. Explain missing capabilities separately from policy restrictions; never turn an effective deny into an ordinary approval prompt.
- **PERM-Q02 — Exceptions and inheritance (resolved):** per-verb filesystem specificity follows PERM-R07; semantic relationships follow PERM-R26. The former complete-operation-set-per-directory authoring default is superseded by independent verb + resource permissions. One-time exceptions, combined effects and Ask controls remain PERM-R19, R21 and R11.
- **PERM-Q03 — Authorization scope and consumption:** lifetime, immutable approvals and approval reuse for retries follow PERM-R23–25; material changes follow PERM-R12. **Default:** keep one-time authority bound to the reviewed action, never infer a task-wide grant. Current Run identity, consumption and retry checks are implemented in the [execution contract](../../docs/features/permissions.md#approval-data-on-decisions); non-Run consumers must define their own durable consumption before enabling effects. [DEC-Q02–04](decisions.md#open-decisions) own continuation and cancellation.
- **PERM-Q04 — Self-modification (deferred):** distinguish user-requested edits from changes initiated by Ash. Ash-initiated Instruction changes still require a Decision under [Instructions](instructions.md#remaining-scope). The general permission-change boundary follows PERM-R16; broader authority for Ash to manage its governing permissions remains deferred.
- **PERM-Q05 — Delivery:** single-permission storage, reviewed overrides, revised authoring, migration and current-tool enforcement are implemented alongside Decisions and the selected evaluator; verification follows the [delivery plan](../../docs/plans/permissions-decisions-tests.md#permission-model). Broader live measurements and new effect adapters remain separate work. Private-data handling and retention/erasure belong to G06/G09.
- **PERM-Q06 — Sensitivity discovery:** keep the selected initial detection scope/thresholds. **Default:** let the Decision offer approval for this action, acceptance/editing of a standing permission, or an explicit response that the concern does not apply. Saving a standing permission is optional. Remember the response for the unchanged action so the same concern is not repeatedly raised; material changes require reassessment. Dismissing a concern does not satisfy an Ask permission or override a deny, and closing the UI supplies no response.

- **PERM-Q07 — Single-permission model (resolved, accepted 2026-10-14):** model and naming follow PERM-R05; authoring follows PERM-R06; conflict resolution follows PERM-R07/R21/R26; UI follows PERM-R15. The [DBML](../data/model.dbml) records the accepted target and the [policy contract](../../docs/features/permissions.md#permissions) defines JSON storage. Implementation status is PERM-Q05.
